ANTES DE EMPEZAR

El mapa mental

Todo el proyecto hace una sola cosa:

  1. 1Vos escribís un objetivo.
  2. 2El harness se lo manda al modelo junto con la lista de herramientas.
  3. 3El modelo responde: o texto final, o “quiero usar estas herramientas”.
  4. 4Si pidió herramientas, el harness las ejecuta y le devuelve los resultados.
  5. ↺Vuelve a preguntarle al modelo — y esto se repite.
  6. 5Cuando responde sin pedir herramientas: terminó.

Eso es un agente. El resto del código existe para que ese ciclo no se descontrole: que termine siempre, que no gaste infinito, que valide lo que el modelo devuelve, y que un error no mate todo.

Cómo leer un proyecto así

No leas los archivos en orden alfabético. Seguí el flujo de los datos: primero el vocabulario (qué objetos existen), después el control (quién llama a quién), después los bordes (dónde entran datos de afuera).

  1. Los tests son la especificación. Si no entendés qué hace algo, buscá su test: te dice qué se espera, con un ejemplo concreto.
  2. Los comentarios largos marcan decisiones. Acá no explican qué hace la línea; explican por qué está así.
  3. Corré el código mientras lo leés. Ver el valor real de una variable vale más que diez minutos mirándola.

1.2 ToolCall y ToolResult líneas 97 y 110

Van en par: el modelo emite un ToolCall, el harness produce un ToolResult.

class ToolCall(BaseModel):      # línea 97
    id: str                     # ← la clave de correlación
    name: str
    arguments: dict[str, Any]

class ToolResult(BaseModel):    # línea 110
    call_id: str                # ← apunta al id de arriba
    success: bool               # ← mirá que NO tiene default
Pregunta

¿Por qué success: bool no tiene un valor por defecto como = True?

Ver respuesta

Porque un default optimista convierte cada olvido en un falso positivo.

Si en algún lado se construye un ToolResult apurado sin pasar success y el default fuera True, el harness le dice al modelo “la operación salió bien” y el agente sigue construyendo sobre una premisa falsa. Sin ningún error, sin ningún log.

Al no tener default, Python te obliga a decidir. Es más molesto de escribir y ese es el punto.

Regla: en campos de resultado y de seguridad, el default seguro es el pesimista — o directamente no hay default.

🎓este caso exacto es un ejercicio

El “Fix the bug” de esa clase usa este mismo modelo ToolResult. Si lo hiciste, acabás de ver el arreglo en producción.

El mismo criterio vuelve en los permisos: el default de un permiso desconocido nunca es ALLOW.

1.3 El validador de coherencia línea 126

@model_validator(mode="after")
def _coherent(self) -> ToolResult:
    if self.success and self.error is not None:
        raise ValueError("un resultado exitoso no puede traer error")
    if not self.success and not self.error:
        raise ValueError("un fallo debe explicar por que fallo")

mode="after" corre después de validar cada campo por separado, así que puede razonar sobre la relación entre campos — algo que ningún campo suelto puede expresar. La segunda regla es la importante: un fallo está obligado a explicar por qué falló.

1.4 as_content() línea 134

def as_content(self) -> str:
    if self.success:
        return self.output or "(sin salida)"
    return f"ERROR: {self.error}"
Pregunta

Cuando una herramienta falla, ¿por qué el error se convierte en texto que vuelve al modelo en vez de lanzar una excepción?

Ver respuesta

Tu instinto de backend dice: falla rápido y ruidoso.

Pero en un agente eso significa que la tarea entera muere porque el modelo probó una ruta razonable que resultó no existir. Un humano haría ls y probaría otra vez.

Con excepciones propagando, un agente de 20 pasos tiene ~20 oportunidades de morir por algo perfectamente recuperable.

Devolviendo el error como texto, el modelo lee “no existe src/mian.py” y en el próximo turno pide list_files. Se autocorrige sin que escribas una línea de lógica de recuperación.

Ahí está la regla para decidir qué sí debe cortar la ejecución: credenciales inválidas, presupuesto agotado, el mismo error tres veces.

2.1 El estado del loop líneas 85-97

messages: list[AgentMessage] = [...]   # la conversación
tokens_in = 0                          # cuánto gastamos
tokens_out = 0

Seis variables locales. No están escondidas en self, y eso es a propósito.

Pregunta

¿Por qué importa que el estado esté en variables locales explícitas?

Ver respuesta

Porque esta tupla exacta es lo que más adelante hay que guardar en disco para que el agente sobreviva a un crash y retome donde estaba.

Lo que es fácil de nombrar es fácil de serializar. Si el estado estuviera repartido en diez atributos mezclados con conexiones HTTP y handles de archivos, guardar y restaurar sería un problema.

Fijate también en time.monotonic() y no time.time(): monotonic sólo avanza. time.time() puede moverse para atrás si el sistema ajusta el reloj (NTP, cambio de horario), y ahí tu presupuesto se vuelve loco.

🎓a dónde lleva esto

Esta tupla es exactamente lo que ahí se serializa. La regla de esas clases —datos se persisten, recursos se reconstruyen— es la razón de que acá no haya ninguna conexión HTTP mezclada con el estado.

W6·C36 — State persistence W6·C37 — Checkpoints

2.2 La composición de presupuestos líneas 119-137

for turn in range(task.max_turns):
    remaining = deadline - time.monotonic()
    if remaining <= 0:
        return finish(..., reason=FailureReason.WALL_CLOCK, turns=turn)

    response = await asyncio.wait_for(
        self.provider.complete(messages, definitions, system=system),
        timeout=min(self.cfg.request_timeout_s, remaining),
    )

Primero verificás, después llamás al modelo. Al revés ya gastaste la llamada que sabías que no podías pagar — y con contexto grande esa última llamada puede ser la más cara de todas.

Pregunta

El for turn in range(max_turns) ya limita las iteraciones. ¿Por qué hace falta además un timeout?

Ver respuesta

Porque limitar iteraciones no es lo mismo que limitar tiempo. Hay dos tipos de terminación y necesitás los dos:

  • Lógica — el loop hace una cantidad acotada de vueltas. La da el for.
  • Temporal — el loop termina en tiempo acotado. La da el wait_for.

Sin la segunda, un solo turno puede colgarse para siempre: si el servidor acepta la conexión y nunca responde, nunca llegás a la segunda iteración. El límite de 20 turnos es irrelevante. En producción eso es indistinguible de un deadlock: el agente no falla, se queda quieto.

Y el min() es la parte fina: el turno tiene su límite, pero nunca puede pasarse del presupuesto total que queda. Si quedan 8 segundos, el turno tiene 8.

🎓dos clases, y un ejercicio que ya hiciste

2.3 max_tokens no es un final válido líneas 162-170

if not response.tool_calls:
    if response.stop_reason is StopReason.MAX_TOKENS:
        messages.append(AgentMessage(role="user", content="Tu respuesta quedo cortada. Continua."))
        continue

Si el modelo llegó al techo de tokens a mitad de una frase, no hay tool calls — así que sin ese if, el código haría return de un texto cortado como si fuera la respuesta final. Nadie se entera: no hay excepción, el estado queda COMPLETED, y el resultado es basura.

Fijate que es continue, no return: consume un turno del presupuesto, que es lo correcto.

Ya hay límite de turnos, de tiempo y de tokens. ¿Para qué una cuarta condición?

Ver respuesta

Porque un modelo atascado no viola ninguna de las otras tres. Tiene presupuesto de sobra: está leyendo el mismo archivo tres veces esperando que cambie.

2.5 La línea más importante del proyecto líneas 201-204

by_id = {r.call_id: r for r in results}
missing = {c.id for c in response.tool_calls} - set(by_id)

Pregunta

¿Por qué armar un diccionario por call_id en vez de recorrer las dos listas con zip(calls, results)?

Ver respuesta

Porque las herramientas se ejecutan en paralelo y el orden de finalización no es el de pedido.

Si el modelo pide leer main.py (800 ms) y README.md (50 ms), el README termina primero. Correlacionando por posición, el modelo recibe el contenido del README etiquetado como main.py.

Y acá está lo peligroso: eso no produce ningún error. Los dos son strings válidos. El modelo razona impecablemente sobre datos que tu harness corrompió, y el síntoma se ve como “el modelo alucina”.

Es el bug que se diagnostica mal casi siempre: se cambia el prompt, se prueba otro modelo, se sube el contexto — y el bug determinista sigue ahí.

El raise de abajo es una red de seguridad: si falta un resultado es un bug nuestro y queremos que explote fuerte.

🎓el concepto más repetido de toda la Academy

La regla que sale de ahí: cuando el síntoma es “el modelo alucina”, sospechá primero de tu harness. Lo vas a comprobar vos mismo en el Experimento 1.

3.3 El except Exception línea 149

Pregunta

¿Por qué except Exception y no except BaseException?

Ver respuesta

Porque asyncio.CancelledError hereda de BaseException, no de Exception.

Con except BaseException atraparías las cancelaciones y romperías todo el sistema de timeouts sin darte cuenta: el wait_for de más arriba quedaría esperando a una corrutina que decidió ignorar el pedido de cancelar.

Ese detalle de una palabra es lo que hace que los timeouts anidados funcionen.

🎓el ejercicio de esta función

El build te hace escribir esta validación, incluido por qué except ValidationError y no except Exception: atrapar todo haría que un bug tuyo se le reporte al modelo como culpa suya, y el modelo intente corregir algo que no puede arreglar.

Por dos razones, y ninguna es “por si acaso”.

La primera: el número del roadmap era de una RTX 4090 con qwen3:14b, que pedía tres read_file en un turno. En un MacBook M1 con gemma4:e4b, que pide uno por turno, la misma tarea pasó de 3 turnos y 7.9k tokens a 11 turnos y 67k. El turno más pesado tocó 12.333 de 32.768. El mismo código, en otra máquina, 2,5× más cerca del techo.

La segunda, la importante: no podés presupuestar lo que no medís. ContextBreakdown es la medición que el propio PROJECT_STATE.md pone como prerequisito de esta fase. Construir el medidor no es adelantarse a la optimización: es la condición para saber si hace falta.

Fijate el orden: primero la instrumentación, después el presupuesto, y la compactación sólo se activa cuando el presupuesto se rompe. Con num_ctx=32768 el compactador está en el código y nunca se ejecuta. Eso es lo correcto.

6.2 Estimar tokens sin tokenizer líneas 56-120

def estimate(self, text: str | None) -> int:
    if not text:
        return 0
    return int(len(text) / self.chars_per_token) + 1

Dividir por 3.6 y listo. Pero eso solo sería adivinar, así que hay una segunda mitad:

def observe(self, estimated: int, actual: int) -> None:
    implied = self.chars_per_token * (estimated / actual)
    if not (_MIN_RATIO <= implied <= _MAX_RATIO):
        return   # fuera de rango: no le creemos a esta muestra
    self.chars_per_token += _EMA_ALPHA * (implied - self.chars_per_token)
Pregunta

¿De dónde sale actual, y por qué esto no es una heurística?

Ver respuesta

Sale de prompt_eval_count, que Ollama devuelve en cada respuesta: es el conteo real del tokenizer del modelo. El loop se lo pasa de vuelta al estimador en loop.py, justo después de acumular los tokens del turno.

O sea que el estimador arranca siendo una heurística y a los pocos turnos se convierte en una medición calibrada contra el tokenizer de ese modelo en particular. Sin tiktoken, sin saber cuál tokenizer usa, sin una dependencia por modelo.

En la corrida de arriba arrancó en 3.60 con un ratio real de 2.90 y llegó a 3.15 en 9 muestras. No convergió del todo, y es a propósito: _EMA_ALPHA = 0.25 prefiere converger despacio a saltar por un turno atípico. Un agente que reestima su presupuesto de golpe por un archivo raro es peor que uno que se equivoca un 8% de forma estable.

El patrón general: estimá antes de gastar, medí después de gastar, y usá la medición para mejorar la estimación. Es lo mismo que hace un planificador de queries con sus estadísticas.

6.4 Reservar lugar para la salida líneas 205-230

@dataclass(frozen=True)
class ContextBudget:
    limit: int
    reserve_output: int = 4_000
    keep_recent_messages: int = 4

    @property
    def available(self) -> int:
        return max(0, self.limit - self.reserve_output)
Pregunta

num_ctx es 32768. ¿Por qué available devuelve 28768 y no 32768?

Ver respuesta

Porque la ventana se comparte entre lo que el modelo lee y lo que el modelo escribe. No son dos presupuestos: es uno.

Si llenás 32.768 tokens de input, el modelo no tiene lugar para responder. Y el fallo es traicionero: los turnos con tool calls son cortos (20-40 tokens de salida), así que todo funciona… hasta el último turno, el del entregable, que necesita 800 y se corta a la mitad.

Ese es exactamente el StopReason.MAX_TOKENS que el loop de la Sesión 02 trata como “no es un final válido”. Las dos mitades del mismo problema: el loop reacciona a la respuesta truncada, el presupuesto evita que pase.

Regla: un presupuesto que no reserva lugar para el resultado no es un presupuesto.

6.5 Compactar sin silencio líneas 288-330

Cuando la conversación no entra, se compactan observaciones viejas. Lo que queda en su lugar:

[observacion compactada: read_file habia devuelto 4210 caracteres
 que ya no estan en el contexto. Si los necesitas, volve a pedir la tool.]
Pregunta

Se compactan los tool results y nunca el razonamiento del assistant. ¿Por qué en ese orden y no al revés?

Ver respuesta

Por valor por token, que es la única métrica que importa acá.

Un read_file de 4000 caracteres ya cumplió su función: el modelo lo leyó y en el turno siguiente escribió qué concluyó. La conclusión son 40 tokens y el archivo 1100. Lo caro es lo redundante.

El razonamiento del assistant es lo contrario: chiquito, y es el único registro de por qué el agente hizo lo que hizo. Borrarlo lo obliga a redescubrir su propio plan, que es la receta para que entre en loop — el LOOP_DETECTED de la Sesión 02.

Y la task no se toca nunca, por una razón que no admite discusión: sin ella el agente no sabe qué está haciendo.

Lo del marcador es la misma regla que _truncate de la Sesión 03: si el modelo cree que vio un archivo entero cuando no lo vio, razona sobre información faltante sin ninguna señal. El marcador convierte un agujero invisible en una instrucción accionable.

El hallazgo de grounding, y por qué es W3

En la primera corrida real el agente respondió sin leer un solo archivo, infiriendo de los nombres. Lo arreglamos con el system prompt y pasó a leer 3. Pero eso es una mejora probabilística.

La garantía dura es un verifier de trayectoria: rechazar la respuesta final si el agente no leyó ningún archivo. Es exactamente el principio de esa clase —la afirmación del modelo no es evidencia— y el chequeo se escribe sobre outcome.trajectory, que ya existe.
